## P0: безопасность до реальных пользователей

### 1. Учитель может управлять чужими пользователями

`src/modules/check_permission/service.py`, check_role_and_id разрешает любому учителю произвольный target_user_id. Проверка применяется к изменению профиля, аватара и пароля. Ограничения «только мои ученики» нет; учитель может затронуть и другого учителя. `/users/students` возвращает всех учеников; `/users/{user_id}` раскрывает профиль, включая email, любому авторизованному пользователю.

Подтверждено прямым вызовом проверки с чужим ID. Требуется явная связь учитель—ученик многие-ко-многим, фильтрация списков и проверка объекта в каждом сценарии.

### 2. Учитель видит чужие курсы

`src/modules/courses/views.py`: без my_courses фильтр teacher_id остаётся None, поэтому возвращаются все курсы; teacher_user_id позволяет выбрать другого учителя. Получение курса по ID разрешено любому учителю. При изменении/удалении курса проверка владельца есть — проблема не во всех операциях одинаковая.

### 3. API возвращает хеш пароля

`src/modules/auth/views.py`: регистрация, регистрация по мастер-паролю и смена пароля имеют response_model=UserDTO. `UserDTO` содержит hashed_password. Нужно отделить внутренний DTO от публичных ответов. Не удалять хеш из внутренней модели входа без замены архитектуры DTO.

### 4. Отозванные refresh-токены принимаются повторно

`src/modules/refresh_tokens/repository.py`: validate_refresh_token проверяет срок, но не is_revoked. Подтверждено на искусственном токене в SQLite. Ротация должна быть атомарной; нужны проверки повторного и параллельного запроса. Токены хранятся открытым текстом. Logout не сопоставляет переданный refresh с текущим пользователем. Политику отзыва access-токенов и смены пароля согласовать отдельно.

### 5. Блокировка пользователя фактически не блокирует вход

`src/modules/auth/auth_service.py`: login и get_current_user не проверяют is_active; refresh тоже не проверяет блокировку. Подтверждено вызовами AuthService с искусственным неактивным пользователем и подменёнными зависимостями.

### 6. Регистрация и роли требуют пересмотра

В UserRole только teacher/student. Глобального администратора нет. Учитель передаёт роль создаваемого пользователя и может создавать учителей. Регистрация по мастер-паролю доступна без пользовательской сессии. Мастер-пароль нельзя считать полноценной ролью администратора; нужны ограничения создания ролей, безопасная процедура первого администратора и аудит действий.

## P1: БД и корректность сценариев

### 7. Текущая миграция не запускается и не соответствует моделям

`src/migrations/versions/d98c55d6402c_.py`: у courses.id аргумент autcrement вместо autoincrement. Генерация SQL PostgreSQL через Alembic Operations без подключения к БД завершилась TypeError.

В миграции отсутствуют is_deleted и deleted_at для courses и student_courses; вместо них остались is_active. Одного исправления опечатки недостаточно. Нужна проверка чистой установки и обновления существующей БД. В dev заменена исходная начальная миграция main; если старая БД уже существует, прямой upgrade между ветками не подготовлен. До решения выяснить, есть ли реальные данные и применённые миграции.

### 8. Удаление занятия с участниками ломается

`src/modules/lessons/repository.py`: DELETE lessons без удаления LessonStudent и следующих зависимостей. У FK нет ON DELETE CASCADE; ORM-каскад сам по себе не выполняется при таком bulk DELETE. На SQLite с включёнными FK подтверждена ошибка даже для занятия с одним участником. Нужно удалить цепочку файлов попыток → попыток → ДЗ/лекций → участников → занятия в одной согласованной операции БД; очистку файлов выполнять с учётом результата транзакции. Полное удаление курса имеет аналогичную проблему зависимостей, выявленную по коду.

### 9. Открепление сохраняет данные, но доступы расходятся

`StudentCoursesService.unenroll_student` уже вызывает soft_delete, не удаляя учебные таблицы — требование о сохранении данных частично реализовано.

Но `CourseRepository.get_courses_by_student_id` не фильтрует StudentCourse.is_deleted: откреплённый курс остаётся в списке ученика. Подтверждено в SQLite. Проверка доступа по ID учитывает is_deleted, но не expires_at, хотя список учитывает срок. Получение занятий, лекций и ДЗ опирается на LessonStudent; централизованной проверки доступа после открепления нет. Нужно разделить сохранение истории в БД и разрешение её просматривать. Восстановление зачисления уже предусмотрено.

### 10. Несогласованная работа со временем

В попытках ДЗ вызывается datetime.now(UTC).replace(tzinfo=None), хотя колонки timezone=True. Это потенциальная ошибка asyncpg и неоднозначное хранение времени. PostgreSQL-проверка не выполнена. Статусы попытки и дата submitted_at тоже требуют согласования: новая попытка имеет DRAFT и уже заполненное время сдачи.

### 11. Дополнительные проверки доступа и контрактов

- В LessonsService.get_lessons отсутствие профиля учителя/ученика оставляет фильтр None: возможна выдача общего списка вместо отказа. Найдено по коду.
- JWT с корректной подписью, но без exp принимается; подтверждено локально. Некорректный sub может вызвать TypeError/ValueError вместо ошибки авторизации.
- Номер попытки вычисляется как max+1; уникальное ограничение есть, но параллельные отправки требуют обработки конфликта.
- Для StudentCourse нет уникальности пары student_id/course_id: параллельное зачисление может создавать дубликаты и ломать scalar_one_or_none.
- Проверка username OR email допускает пересечения идентификаторов разных аккаунтов.
- Не все доменные NotFound/AlreadyExists исключения зарегистрированы как 404/409; часть уходит в общий 500.
- Оконный count для списка занятий возвращает total=0 при offset за концом списка, даже когда строки существуют.

## P1/P2: окружение, файлы и эксплуатация

- Нет .env.example и инструкции с полным набором переменных и командами старта. README существенно отстаёт от dev.
- Нет CI, процедуры резервного копирования/восстановления, мониторинга и готового healthcheck приложения.
- Compose содержит фиксированный пароль PostgreSQL и открывает порт БД. Это конфигурация для локальной разработки, её нужно переработать перед публикацией сервера.
- Dockerfile не устанавливает LibreOffice, хотя обработка doc/docx/odt/txt вызывает soffice. Изображение Docker не собиралось; работоспособность конвертации документов в нём не подтверждена.
- Нет .dockerignore; COPY . . может включить локальную .env, .venv и медиа в образ. .gitignore не защищает Docker build context.
- В загрузках читается весь файл в память; не найдены ограничения размера и квоты. Расширение не заменяет проверку содержимого.
- Работа с файлами и CPU-конвертация местами синхронны внутри async-функций; нужны лимиты, таймауты и отдельное выполнение тяжёлой обработки.
- Удаление/замена файлов и транзакция БД не всегда согласованы; исключения очистки местами подавляются. Возможны осиротевшие файлы и потеря файла при неудачной записи БД.
- Config/engine создаётся повторно, lifespan не освобождает ресурсы. Встроенный запуск src/main.py использует uvicorn.run внутри asyncio.run и строку main:app; Compose использует более подходящую команду uvicorn src.main:app.
- Не найдены rate limiting входа, подтверждение email, восстановление пароля и журнал административных действий.

## Соответствие rules_project.md

Правила прочитаны полностью и принимаются как основа дальнейших изменений:

1. src/modules/<domain>/{models,models_dto,repository,service,depends,views,exception}.py.
2. SQL в репозитории; транзакции и бизнес-правила в сервисе; views только вызывают сервисы.
3. Mapped/mapped_column, ORMDTO, model_validate/model_dump, типизация и async I/O.
4. Модели регистрируются в db_models; роутеры в api/app.py; исключения в обработчиках.
5. Медиа через config.paths/PathBuilder и существующие обработчики; изменения схемы через Alembic.
6. Тесты зеркалят модули, используют фабрики, comparison_models и изолированную БД.
7. В публичном контракте user_id, а не внутренние teacher_id/student_id.

Есть расхождения правил и существующего кода: правила указывают BaseRepository в base/database_model, но фактически класс находится в base/repository_model. В views курсов есть прямые обращения к репозиториям, в сервисе попыток — прямой SQL. Не все функции типизированы, не все роуты имеют явные status_code/response_model. Следовать архитектурному смыслу правил и актуальному классу, не копировать эти нарушения. Для бинарных/204 ответов использовать соответствующий HTTP-контракт, не вводить фиктивный JSON response_model.

## Согласованные требования из разговора

- У одного ученика может быть несколько учителей — явно подтверждено владельцем.
- Учитель создаёт учеников, работает только со своими учениками и курсами.
- Глобальный администратор имеет доступ ко всем пользователям и курсам с фильтрацией.
- При удалении занятия удаляются лекции, ДЗ и попытки решения; связанные файлы также требуют очистки.
- При откреплении от курса связанные учебные записи сохраняются.
- Учитель видит свои удалённые курсы; будущий фронтенд помечает is_deleted=true как «Архивирован».

Эти требования записаны, но в рамках аудита не реализованы. Не решены: как второй учитель получает доступ к существующему ученику; кто может менять общие данные ученика; что ученик видит после открепления; разрешено ли восстановление курса и полное удаление курса.

1. Продуктовое интервью и матрица прав; определить существующие данные/серверы и модель учебных материалов.

4. Связь учитель—ученик, администратор с фильтрами, согласованное открепление/архив/удаление и проверки сохранения данных.
5. После согласования MVP — фронтенд и сквозные сценарии по одному модулю.
6. Перед реальными пользователями — применимые требования к персональным данным, инфраструктура, восстановление бэкапа и ограниченный пилот.
