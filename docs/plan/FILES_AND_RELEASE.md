## Хранение без привязки домена к диску

T12a вводит маленький `Storage` protocol: put(stream,key), open/get(key), delete(key), stat(key). `LocalStorage` использует config.paths/PathBuilder; позже `S3Storage` реализует тот же контракт. Не тянуть boto3/MinIO в обязательный локальный старт. Storage не решает права — это service доменного владельца. Сетевой adapter должен быть async либо явно выносить blocking SDK из event loop.

В БД — storage backend/key, размер, MIME по проверке, hash, safe display name, состояние pending/ready/failed, uploader, timestamps. `FileAsset` (новый files module) описывает бинарный объект; явные FK из Lecture/Homework/HomeworkSubmissionFile сохраняют принадлежность домену. Не делать полиморфный owner_type/id единственным механизмом ссылочной целостности. Существующие пути сначала читаются legacy adapter, затем отдельным migration job копируются и сверяются. Переходный период чтения old/new ограничен, клиент видит стабильный file_id/download URL, не абсолютный путь.

Бинарные данные не в PostgreSQL. Ключ — UUID без исходного имени/ФИО. Имя пользователя — только подпись после нормализации; нельзя включать его в filesystem path. Path traversal, symlink escape и `..` блокируются. Дедупликация по hash только в проверенном scope; не глобальный API «есть ли у другого ученика такой файл».

Upload: auth/owner check → byte stream в temp с лимитом → проверка сигнатуры/декодера → bounded normalization → запись final immutable key → DB ready/link commit. При failure before commit удалить новый объект или записать orphan для GC; старый остаётся доступен. При swap commit сначала меняет ссылку, потом durable deletion queue удаляет старый. Нельзя гарантировать общую транзакцию БД+диск, нужен compensation и reconciliation. Pending файлы не скачиваются.

## Ограничения первой версии (D06)

| Параметр | Стартовая рекомендация | Проверка |
|---|---|---|
| Форматы | PDF, JPEG, PNG, WebP, HEIC/HEIF; статические изображения | Переименованный exe, SVG/HTML, битый PDF, анимация и неизвестный MIME отклоняются |
| Размер файла | 20 MiB исходник, лимит по потоку независимо от Content-Length | Ложный/отсутствующий header не обходит лимит |
| Файлов в ответе | 10; сумма исходников до 100 MiB | Ограничение по сохранённым+новым, включая concurrent uploads |
| Изображение | До 50 MP до декодирования, один кадр | Decompression bomb, huge dimensions, HEIC sequence |
| Конвертация | Один процесс обработки сначала; hard timeout 30 секунд как начальная гипотеза | Битый файл не держит очередь; процесс можно завершить и очистить |
| Квота | Предупреждения по курсу/пользователю; 1 GiB на ученика как начальный контролируемый лимит, admin может увеличить | Не отрезать уже загруженные материалы, понятное сообщение и помощь |

PDF 2–3 МБ хранить один раз: текущая двойная копия original/pdf не нужна. Содержимое не растеризовать ради «сжатия»: текст/векторные формулы сохраняют качество. Встроенный просмотр PDF делать безопасным отдельным viewer/контекстом, скачивание всегда доступно; исходный PDF не становится безопасным только от проверки заголовка. На production предусмотреть локальное сканирование/карантин, не отправлять ученические файлы в публичные malware-сервисы. Не обещать поддержку docx/odt только потому, что handler их содержит: либо оставить feature flag выключенным в MVP API/UI, либо до включения добавить LibreOffice в контейнер, изоляцию/timeout и тесты. Код обработчика не удалять.

## Фотографии домашних работ

Переиспользовать Pillow 12.3 + pillow_heif 1.5, уже в проекте; отдельный алгоритм с нуля не нужен. Предлагаемый конвейер T12b:

1. Потоковая загрузка в приватный temp. Проверить bytes, формат, pixels, frames. HEIC-декодер проверить в целевом Linux image.
2. EXIF orientation → RGB/sRGB по проверенной поддержке профиля → удалить GPS/EXIF/XMP; фон для прозрачного изображения белый.
3. Сохранять proportion, не увеличивать; кандидат: длинная сторона 2560 px, WebP quality 85. Эти значения проверяются на мелких дробях/степенях/карандаше/бликах, не только на фото природы. Не использовать аватарный размер для тетради.
4. Preview до подтверждения: zoom, повторная загрузка, объяснение ошибки. Если текст плохо читается — поднять разрешение/качество или безопасный lossless вариант; не понижать качество бесконечно ради целевого размера.
5. Целевой средний размер 0.5–1.5 МБ — гипотеза для расчёта, не SLA. Вариант без JPEG→WebP→PDF тройного хранения. Для просмотра/скачивания нормализованное изображение; PDF ответ ученика не генерировать автоматически.
6. Исходник до успешного подтверждения/commit, затем удаляется по D06; эту необратимую политику согласовать и объяснить пользователю до пилота. Пока D06 не решён, не удалять существующие оригиналы массово. Для PDF оригинал сохраняется.

CPU-конверсию вынести из async event loop; hard timeout требует процесса/worker, отмена await thread не останавливает исполняющийся декодер. Для MVP один локальный subprocess с ограничением памяти/времени и очередью; при росте — worker, не обязательный Redis сейчас.

QA набор synthetic: обычная тетрадь 12MP, HEIC с поворотом, 48MP, мелкая дробь, бледный карандаш, PNG скриншот, испорченные/переименованные файлы, 20MiB boundary, 11-й файл, parallel quota, timeout, disk full, DB rollback. Учитель визуально подтверждает читаемость на desktop и телефоне.

## Оценка объёма

Допущение для расчёта: 60 учеников × 2 урока/нед × 4.33 недели ≈ 520 ученико-занятий/месяц; 1 PDF 3 МБ + 5 фото на занятие. Реальная частота неизвестна, это прозрачный сценарий, а не прогноз.

- С фото по 0.8 МБ: `520 × (3 + 5×0.8)` ≈ **3.64 ГБ/месяц**, около 44 ГБ/год активного контента.
- С исходниками по 5 МБ: `520 × (3 + 5×5)` ≈ **14.56 ГБ/месяц**, около 175 ГБ/год.
- Preview, повторные ответы, служебные файлы, версии и backups добавляются отдельно. Две полные копии активных данных ≈ ещё 88 ГБ/год в первом сценарии; rotation/incremental меняют расчёт.

Не закупать объём по этим цифрам. На пилоте измерить медиану/p95 файла и фактическое число загрузок; алерты на 70/85% диска/квоты, лимит temp, отдельный запас для restore. Архив продолжает занимать место; срок хранения решает P01, а не желание заполнить диск.

## Доступ к скачиванию и S3

MVP: authenticated streaming endpoint, проверка Course→StudentCourse/LessonStudent→file на каждом чтении; корректный Content-Type, nosniff, безопасный Content-Disposition и private/no-store для чувствительных ответов. Не public StaticFiles mount `/media`. PDF preview и Range запросы тоже проверяют auth. Ссылки в уведомлениях ведут на доменный экран, а не вечный объектный URL.

S3 позже: приватный bucket, РФ-регион, отдельные credentials минимальных прав, key layout без ПД, encryption/backup policy по выбранному провайдеру. Presigned URL короткий (предложение 60 секунд) выдаётся после проверки; это bearer-ссылка, отзыв доступа не отзовёт уже выданный URL мгновенно. Если требуется немедленный отзыв — proxy download. Перед переключением: manifest key/hash/size, копирование, сверка, canary reads, dual-read, сохранение старых объектов до подтверждённого rollback window; garbage collection отдельно.

## T17/P02: подготовка и выпуск на Timeweb

1. Узнать из панели конкретный продукт: VPS/Cloud или shared hosting, ОС/архитектура, регион, свободный диск, CPU/RAM, имеющиеся приложения, домен/DNS, backup. Нельзя переустанавливать уже используемый сервер или открывать порты наугад.
2. По нагрузке сначала один API instance + PostgreSQL + proxy; размер проверить 10 одновременными uploads и 20 сессиями. 2 vCPU/4 GiB — лишь отправная точка оценки стенда, не обещание вместимости при HEIC-конверсиях.
3. Отдельный production compose: pinned images, no reload, non-root app, read-only filesystem где подходит, отдельные writable media/temp, restart policy, health/readiness, graceful shutdown. PostgreSQL не публикуется в интернет. SSH по ключам, firewall, секреты в защищённом файле вне Git/image, proxy 80/443 и HTTPS.
4. Создать release candidate из проверенного SHA, собрать immutable image/frontend. Проверить образ на .env/.git/.venv/private media, зависимости и лицензии. OpenAPI закрыть/защитить по решению; readiness проверяет БД, liveness не раскрывает настройки.
5. Сначала synthetic staging. Потом backup текущей production БД/media и контроль restore, migration preflight `current/heads`, окно изменения, совместимость схемы и приложения. Миграции отдельным job, не одновременно каждым API worker.
6. До внешней публикации все G4/P01 и отдельное явное поручение владельца на конкретный deploy. DNS/TLS/smoke: login, 2-teacher isolation, upload/download, проверка, logout, archive. Production данные не подставлять в CI.
7. Rollback: предыдущий image совместим только при expand/contract миграциях. При destructive migration rollback требует restore в согласованном окне с потерей поздних записей; не выполнять автоматический downgrade на live. Остановить writes, оценить последствия, решение владельца.
8. Выпуск в main — только после готовности; main сейчас исторический шаблон. PR dev→main не «чинит» production автоматически. Записать release SHA, дату, schema revision, runbook и ответственного.

## T18: backup и восстановление

Предложение начальных целей: RPO ≤24ч, RTO ≤4ч для малого пилота; утвердить перед запуском. Ежедневный PostgreSQL logical backup и согласованный media manifest, отдельная защищённая копия вне VPS в РФ, шифрование и доступ отдельной роли. Для малого MVP короткое maintenance окно делает согласованную БД+media копию проще; при online backup учитывать неизменяемые key и приостановку GC. Хранение 7 daily + 4 weekly — технический кандидат, не срок законного хранения всех ПД.

Проверка восстановления на отдельный стенд: restore DB, objects, checksum referenced files, schema revision, login synthetic/admin test, чтение архивов и двух учителей; применить deletion ledger; измерить время. Ежемесячный rehearsal и перед опасной миграцией. Снапшот провайдера — дополнительная мера; [Timeweb прямо описывает ограничения копий и рекомендует удалённые копии](https://timeweb.cloud/docs/cloud-servers/manage-servers/backup).

Мониторинг: uptime/readiness, 5xx и latency, очередь/ошибки обработки файлов, свободный диск/temp, DB connections, age последнего успешного backup, провалы auth без логирования токенов. Алерт должен иметь адресата и действие. Runbook инцидента: ограничить затронутый доступ, сохранить минимальные доказательства, оценить данные, восстановить безопасный релиз, включить процедуру PRIVACY.
