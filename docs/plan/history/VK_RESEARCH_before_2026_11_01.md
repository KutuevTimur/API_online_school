### Принято01.11.2026: невозможность доставки и набор уведомлений

Владелец подтвердил: если родитель записал ребёнка, а бот не может написать
ребёнку, **запись не блокировать**. Родителю дать понятную инструкцию открыть
бота с аккаунта ребёнка и разрешить сообщения для напоминаний. Не обещать
доставку лишь на основании успешной брони/parent link. Владелец отдельно требует
тщательной проработки ошибок и границ этого сценария до реализации.

Принятый первый набор (короткий текст + переход в кабинет для ДЗ/review):

| Адресат | События |
|---|---|
| Ребёнок | Выдано ДЗ; работа проверена; занятие перенесено/отменено; прежний reminder20min |
| Преподаватель | Ученик записался; отправил решение на проверку |
| Родитель | Сохранить нынешние сообщения о заявке на отмену и её результате; ДЗ/оценки не дублировать |

Не добавлять родителю ДЗ/оценки автоматически при разрешении сообщений.
Привязка кабинета, parent relation и разрешение VK на сообщения — отдельные
состояния. Пока кабинет не активирован, кнопка не должна обходить приглашение
или открывать чужие материалы; return URL локальный/валидированный.

Обязательные пункты последующего технического исследования/карточек:

- Доменный результат брони хранится независимо от доставки; timeout отправки
  не повторяет создание занятия. Повтор пользовательского confirm/входящего
  события возвращает тот же receipt, а не вторую встречу.
- Отдельно различать «точно запрещены сообщения» и «сбой/неизвестен результат»;
  техническую ошибку не объявлять отсутствием согласия. VK API contract/реальные
  коды проверить официально; сейчас это требование к состояниям, не готовый код.
- Проверять право отправки/актуальную связь при выполнении задания; отписка,
  отвязка, блокировка, архив/окончание доступа должны остановить недопустимое.
- Временный сбой → ограниченный retry доставки с тем же dedupe/random_id;
  запрет → остановка. Срок актуальности событий/напоминаний определить отдельно,
  не отправлять просроченный reminder после начала занятия.
- Новое разрешение сообщений не означает рассылку всех старых уведомлений:
  перечитать актуальные будущие встречи; политика старых событий ещё проектируется.
  Перенос/отмена пересчитывает напоминание, worker повторно проверяет дату/статус.
- Матрица fixtures: родитель записал до первого обращения ребёнка; запрет/allow;
  оба могут писать; transient error/неизвестный результат; дубль; revoke между
  очередью и отправкой; перенос/отмена перед20min; server/local restart.
- Живые проверки сначала только в разрешённом контексте Даниила/получателей,
  без рассылки настоящим ученикам Тимура. Полезная ручная приёмка отдельно от
  source review/fixture tests, без заявления100% доставки.

Остаток интервью об идентичности/доступе: подтверждение parent→child для доступа
к существующему расписанию, безопасная связь старого пользователя бота с уже
созданным аккаунтом платформы. Детали retries/схемы/блокировок agent проектирует
по коду и источникам, не перекладывает техническое проектирование на владельца.

### Подтверждённый сценарий записи · ответы31.10

**Бизнес-поток сохраняется как в существующем боте; менять источник расписания,
не переделывать удачный пользовательский путь. Повторно вопросы ниже не задавать.**

1. Первое обращение: выбор ученик/родитель; родитель связывает ребёнка. Имя,
   фамилия и класс вводятся впервые для **ребёнка**, а не вместо него для родителя.
   При следующих записях используются сохранённые сведения, повторный ввод не нужен.
2. Выбор преподавателя (существующий default из профиля сохраняет привычный путь),
   затем только дни с явно открытыми часами, затем свободный час выбранного дня.
   Кнопки назад/обновить/сменить преподавателя/меню сохраняются.
3. Карточка подтверждения: ребёнок, преподаватель, день и время; пользователь
   нажимает «Подтвердить» и записан **без одобрения преподавателя**, поскольку
   преподаватель заранее открыл время. При гонке проверять доступность при записи;
   успех только после сохранения платформой, а не на основании текста кнопки.
4. Свободные часы публикуются **только на неделю**; автоматическое повторение
   открытых часов не требуется. Дни→часы остаются прежним способом выбора.
   Привязка недели/даты должна быть стабильна при старой кнопке/смене недели;
   бот прежде не хранил конкретную дату, это задача backend-контракта, не новый
   вопрос о желании повторяющихся окон.
5. Постоянное время назначает преподаватель по личной договорённости после
   первоначальной записи (например,10 недель через existing RegularLessonsService).
   Ученик не оформляет регулярную серию ботом. Перенос одной встречи не меняет
   дальнейшую серию. Связь с VK сохраняется независимо от разовости/регулярности.
6. Родитель необязателен; записываться может ребёнок или связанный родитель.
   В обоих случаях получатель занятия — один и тот же ребёнок; родитель смотрит
   его расписание/записывает его. Reminder20min — **ребёнку**, как сейчас.
   Дополнительные ДЗ/оценки/кабинет родителя этим ответом не разрешены.
7. Новая запись должна попасть в расписание платформы; переход от Sheets и
   сохранение доступности старого бота выполняются по отдельному плану испытаний.

Повторно подробно прочитаны **все** обработчики `handlers.py`, клавиатуры
`keyboards.py`, `database.py`, `google_sheets.py`, `reminders.py` и оставшиеся
участки `main.py`; DAYS_MAP/TIME_ROWS извлечены через ast.parse без импорта
config и без вывода ключей/ID таблиц. Это локальный source review, не live PASS.

Важные различия хранения для последующего проектирования: в боте имя/класс сейчас
одна форматированная строка, проверка класса не отдельная; у платформы отдельные
поля и school_grade. Не перезаписывать подтверждённый профиль платформы этим
текстом автоматически. Профиль бота сохраняется **до** проверки занятости,
поэтому наличие профиля не доказывает успешно созданную первую запись/привязку.
Один teacher в JSON — предпочтение меню, не ограничение числа связей в платформе.
Подтверждение родительства и подлинности команд нужно усилить на backend,
сохраняя понятный маршрут; текущие raw URL/кнопки не дают полномочий платформы.

Новые открытые вопросы относятся к отсутствующему соединению систем: когда

Не спрашивать заново о самом маршруте дни→время→confirm, недельных окнах,

### Уточнение владельца31.10: два сценария и пожелание копирования

- **Постоянное время:** ученик первоначально записывался/подключался через бота,
  затем преподаватель сам еженедельно проставлял его в таблице для расписания и
  напоминаний. В платформе использовать существующую регулярность с переносом
  отдельной встречи без изменения последующего постоянного времени. Не считать
  первоначальную запись ботом разрешением бессрочно генерировать Lesson.
- **Разовая запись:** некоторые ученики в начале недели выбирают одно/два занятия
  текущей недели из времени, которое преподаватель **явно открыл**. Отсутствие
  занятия не означает доступность для записи. Это новая политика опубликованных
  окон; текущее право управления расписанием ученику автоматически не выдаётся.
- **Google Sheets:** предпочтительна возможность менять расписание и в таблице,
  и на платформе с отражением результата в обеих. Владелец отмечает, что платформа
  уже удобна; окончательный объём прямого редактирования Sheets и его приоритет
  ещё не утверждены. Не сводить пожелание к согласованному read-only экспорту.
- В речи свободные окна названы зелёными «S». Прочитанный локальный код проверяет
  латинскую `C` независимо от цвета. Зафиксировано расхождение обозначения, не
  основание менять parser/данные или считать серверную версию совпадающей с local.

**Отдельно записать в backlog по прямой просьбе владельца:** преподаватель выбирает
несколько занятий прошлой недели и копирует их на следующую в те же дни/время.
Это создание новых встреч; исходные встречи остаются. Не подменять переносом,
не копировать автоматически учебные материалы/ответы/оценки, не обещать такое
поведение существующего API. Требования к составу копии ещё не утверждены.
Плановая ссылка — [TASKS/F04](../TASKS.md#после-mvp--отдельные-проекты-решения-не-обещанные-сроки).

проверка действующих прав/участия/архива и конфликтов с уже созданными встречами
серии; явное подтверждение, receipt против двойного создания. Цена новых встреч
по текущему D12, а не копирование исторического snapshot. Отдельно решить,

### Уточнение31.10: первый вход, будущая демонстрация и оформление

### Масштабирование и запасное расписание · уточнение31.10

Владелец просит учитывать будущую продажу независимым преподавателям, подписки
и рост числа учеников. Предлагает со временем отказаться от редактирования
Google Sheets и оставить периодически обновляемую таблицу для просмотра при
сбоях. Это новое направление обсуждения вместо обязательной двусторонней правки;
точный момент переключения и формат экспорта ещё не согласованы. Сейчас бот
пишет в Sheets, преподаватель там же публикует свободные часы — это действующий
поток, он не переключался и не считается уже заменённым платформой.

Рекомендация: платформа становится главным хранилищем и единственным владельцем
подтверждённых записей; бот — интерфейс к её сервисам, Google — доступная отдельно
копия для чтения. При недоступной платформе не подтверждать новые брони по старой
таблице и не переключать автоматически запись на второй независимый источник.

Минимальная подготовка к росту без реализации F03 сейчас:

- Приглашения выдаёт преподаватель своим ученикам, ученик сам задаёт пароль;
  это уже распределяет подключение между преподавателями. По текущему D01
  восстановление активированного аккаунта выдаёт admin, self-service reset не
  реализован и не обещается. Автоматизация восстановления — отдельное решение.
- Не выдавать полномочия по выбранной в боте роли, имени преподавателя или
  possession Telegram/VK URL. Подтверждённая identity → текущий User → текущие
  права/связи; несколько преподавателей не требуют копий аккаунта ученика.
- Бот пользуется ограниченным integration доступом; действие привязано к
  подтверждённому пользователю и разрешённому контексту. Не хранить его refresh,
  не давать боту один бесконтрольный admin-доступ ко всем данным/SQL.
- Исходящие задания доставки — постоянные, с retry/dedupe и ограничением темпа;
  допускают дальнейшее увеличение числа workers. Не строить обязательную доставку
  на одном словаре/потоке памяти. Отдельные инфраструктурные сервисы добавляются
  по измеренной нагрузке; микросервисы для первого этапа не нужны.
- До первого независимого клиента F03: organizations/memberships, scoped admin,
  изоляция DB/API/files/кеша/интеграций, двухорганизационные тесты. Текущая изоляция
  teacher внутри LGG не объявляется готовой SaaS-изоляцией. Доменная идентичность
  ученика отделяется от memberships и от тарифа/оплаты.
- Подписки, платежи, лимиты, собственные/общий VK-боты клиентов, обработчики ПД и
  права на историю при окончании подписки требуют отдельных решений F03/P01;
  прекращение платежей не должно молча отменять принятую D02 историю.

Безопасный будущий переход — только отдельной реализацией:

1. Добавить в платформу явные открытые для записи окна с датами, teacher scope
   и контролем конфликтов. Свободный промежуток календаря не равен открытому окну.
2. Подготовить соответствия пользователей/преподавателей и preview переноса
   выбранного периода из Sheets; не превращать weekday-сетку в бесконечную серию.
   Импорт/чтение живых таблиц/миграция users_data.json сейчас не разрешены.
3. Согласовать переключение: конкретный период/расписание имеет один источник
   записи. Перенаправить выбор окон/создание/отмены/reminders бота на платформу;
   исключить одновременное независимое подтверждение одних слотов через Sheets.
4. Проверить запись/перенос/отмену/напоминание, затем включить отдельный экспорт
   для просмотра. План отката должен учитывать уже принятые записи, не терять их.

**Запасная таблица не равна backup:** экспорт помогает увидеть расписание при
сбое, но не восстанавливает материалы, ответы, оценки, права и историю изменений.
Полный backup DB+media+deletion ledger и проверенный restore остаются в T18.
Даже самый частый export может ещё не содержать последнюю подтверждённую запись;
«расписание никогда не потеряется» без измеренных целей/restore не обещается.

Для будущего экспорта предложено: дата/время успешного обновления, timezone и
покрываемый период; понятный возраст копии при сбое, ограниченный read-only доступ
к минимальным сведениям. Не считать неудачную выгрузку успешной, не стирать
последнюю целую копию перед подготовкой новой. История snapshots/backup нужна
отдельно: обычная синхронизация может размножить ошибку удаления. Периодичность и
допустимую потерю последних изменений ещё согласовать, сейчас cron не создавался.
Google/export остаётся внешней передачей данных с нерешёнными вопросами P01.

После уточнения владельца приоритет обсуждения — **VK ID и подтверждённая
привязка** (историческая гипотеза, заменена уточнением выше), затем объединение с существующим ботом. Прежняя рекомендация
«начать с уведомлений» ниже — первоначальная гипотеза, не решение владельца.

Начать с **подтверждённой привязки существующего аккаунта и ограниченных
сервисных уведомлений**; точный первый этап зависит от ответа владельца.
Вход VK ID можно добавить отдельно. Уведомления могут использовать подтверждение
в диалоге сообщества без внедрения VK ID; корректный протокол привязки и ограничения
такого способа ещё проверить. Бот записи — следующий независимый этап.

### Привязка и вход

- Привязка начинается в уже аутентифицированном аккаунте платформы с повторным
  подтверждением личности. OAuth transaction: короткий срок, одноразовость,
  state и PKCE, привязка к текущей сессии и назначению link/login.
- Backend проверяет результат VK по документированному протоколу. Не доверять
  ID из браузера, имени, совпавшему телефону/email или вручную вставленному URL.
- External identity хранится отдельно от User/ролей/участия. Уникальность в
  правильном пространстве provider/app/subject; область идентификатора VK ID и
  способ сопоставления с адресатом сообщений VK нужно подтвердить отдельно.
  Не считать их равными по виду чисел.
- Не создавать автоматически аккаунт, не активировать приглашение и не выдавать
  роль/связь при неизвестной identity. Известной identity выдавать собственную
  сессию LGG только после проверки is_active/is_activated и текущих правил auth.
- Отвязка — с повторным подтверждением и сохранением способа входа/восстановления;
  останавливает связанные доставки/незавершённые операции. Отзыв VK permission,
  выключение уведомлений LGG и отвязка — разные состояния. Сроки удаления
  identity/audit и политика отзыва сессий при отвязке ещё согласуются.

### Доставка и команды

- Событие домена и outbox — одна DB-транзакция. Worker доставляет после commit;
  сбой VK не откатывает занятие и не блокирует обычный кабинет.
- Разделить входящую дедупликацию `(community,event_id)`, receipt бизнес-команды
  и исходящую delivery `(event,recipient,channel)`. Схема VK прямо требует
  игнорировать повтор одного event_id [S3].
- Один сохранённый random_id на повтор отправки, а не новый на каждую попытку;
  точную область/срок дедупликации VK ещё проверить. Не обещать exactly-once.
- Callback: проверка ожидаемого сообщества, секрета/актуального механизма
  подлинности, размера/структуры, сохранение inbox до подтверждения приёма;
  побочные эффекты отдельно. Формат confirmation/ответа и сроки перепроверить.
- Разрешение сообщений VK плюс отдельный выбор категорий в LGG; не трактовать
  подписку на сообщество либо OAuth consent как согласие на всё. Нужный способ
  пользовательского разрешения/первого обращения проверить по актуальным правилам.
- message_deny/ошибка запрета останавливают доставки; технические transient ошибки
  получают ограниченные backoff/retry, постоянные — остановку/диагностику.
  Лимиты настраиваются после проверки, без обещания времени доставки.
- Отписка/отвязка отменяет queued отправки; worker повторно проверяет связь,
  разрешение, актуальность события и права. Поздний allow не должен сам включать
  ранее выключенные пользователем категории. Нужна сверка после потерянных событий.
- Сообщение минимальное: факт/время/ссылка в защищённый кабинет. Полные ответы,
  оценки, файлы, контакты и индивидуальные ставки не передавать по умолчанию.
  Уже доставленное сообщение не становится недоступным вслед за отзывом прав.
- Напоминания «за N часов» требуют отдельного расписания доставки: текущие
  внутренние события не являются готовым таймером. Перенос/отмена должны
  пересчитать/снять старые напоминания, устаревшие сообщения не досылать бессрочно.

### Единое расписание

Платформа остаётся источником истины; бот вызывает прикладные сервисы с
проверенным субъектом и ограниченной командой, не читает/пишет таблицы напрямую
и не хранит пользовательский refresh. При запросе ученика actor остаётся учеником:
нельзя незаметно выдать ему полномочия учителя. Предложение заявки с подтверждением
teacher лучше сохраняет текущую модель, но требует нового согласованного workflow.

Создание/перенос/отмена используют существующие права, архив/cutoff, lock,
expected_updated_at, пересчёт ДЗ и price snapshots. Бот хранит receipt и умеет
прочитать результат после неопределённого исхода. Проверять свободное время
повторно в транзакции подтверждения, а не только при показе кнопок.

Серии используют существующий preview/confirm/revision/receipt; не генерировать
повторно перенесённые/отменённые вхождения. Cancel встречи и archive различны.

для записи, напоминаний и получения информации о школе. Новый бот/сообщество

Текущее серверное состояние/код не проверялись, подтверждённое использование —
со слов владельца. Прошлая запись об остановке сервера не считается текущим фактом.

**Рекомендуемый порядок, ещё не исполнен:**

1. Работающий сервер продолжает прежний Sheets-поток. Изменения локального кода
   сами по себе не загружаются на сервер. Но запуск с тем же боевым токеном
   обращается к тому же сообществу, а не к изолированной «локальной версии VK».
   В прочитанном main.py запуск сразу отправляет сообщение и включает reminders.
2. До запуска нового кода отделить тестовый вход от боевого start_bot и интеграций
   с побочными эффектами при импорте. Полностью синтетические входящие события
   (ученик/родитель/преподаватель), поддельные ответы VK/Sheets и HTTP fixtures
   платформы; отдельные временные данные вне preview/users_data.json. Без боевых
   секретов, Long Poll, внешних отправок/Google writes. Наличие такого режима
   сейчас не подтверждено — его предстоит реализовать отдельным поручением.
3. Проверить весь путь и регрессию: информационные меню/первый контакт; ученик
   записывается сам; родитель пишет от своего VK, получателем занятия остаётся
   ребёнок; запреты чужих прав; запись/дубль/конфликт; отмена и старые кнопки;
   перенос одной встречи; reminder20min и запрет старого; отписка/ошибка доставки.
   Sender VK, target student и подтверждённое право представительства — разные
   сущности; старый parent link не переносится как достаточное доказательство
   права чтения/изменения платформы. Правила первой привязки ещё согласовать.
4. После локальных проверок — отдельное согласование минимального живого теста
   на существующем сообществе: allowlist владельца, изолированные synthetic
   пользователи/слоты backend, никакой записи в настоящие таблицы. Предпочтителен
   ограниченный пилот в **одном** обработчике: новый маршрут только владельцу,
   прежний путь остальным. Это изменение сервера и требует отдельного deploy
   поручения, переключателя/проверенного возврата и предварительной проверки
   фактической серверной версии. Это уже реальный внешний тест, не полная изоляция.
5. Не запускать параллельно независимый локальный start_bot с тем же токеном и
   серверным экземпляром: не предполагать изоляцию получателей/отправок, есть риск
   повторной обработки и двух schedulers. Отдельное ночное окно с одним экземпляром
   возможно лишь как менее предпочтительный вариант по отдельному поручению:
   остановка рабочего бота временно затрагивает клиентов и reminders; ночь сама
   по себе не гарантирует отсутствия входящих. План приёма событий/напоминаний
   во время окна, возврат и ограничения должны быть согласованы заранее.

Связь parent→student — обязательный сценарий для проектирования и проверки,
без автоматического добавления родительского кабинета/ролей в платформу.
Переход с Sheets только после отдельной приёмки; локальные fixture PASS не
выдаются за живую доставку/серверную приёмку. Прежние запреты seed/reset/DB tests
preview/открытия ДЗ58/миграции users_data.json/сообщений без поручения сохраняются.

## Этапы и сложность — без обещания сроков

1. Завершить интервью, правила VK/правовую сверку, определить доступность продукта
   для нашего владельца/сообщества. Результат — согласованный scope, без кода.
2. Отдельно разрешённый минимальный пилот привязки + одного типа уведомления на
   synthetic стенде. Inbox/outbox, revoke/retry, тесты подделок/повторов/чужих ID.
3. При необходимости отдельный VK ID login с собственной сессией LGG и проверкой
   account takeover/link collision/отвязки. Не заменяет ручную выдачу доступа.
4. Отдельная запись ботом: сначала заявки/teacher confirmation либо команды teacher,
   после решения сценария. Строгая самостоятельная бронь сложнее: окна, состояние
   заявки, атомарные конфликты, receipts и гонки с платформой/сериями.

Относительно: привязка/login — средняя сложность с высокой ценой ошибки auth;
надёжные уведомления — средняя; запись с подтверждением — средняя/высокая;
самостоятельная бронь и массовые изменения серий — высокая. Оценка в днях пока
не обоснована: зависит от существующего бота, доступов VK, состава событий,
модели брони, размещения/домена, требований несовершеннолетних и delivery SLA.
Все прежние S2/S3/S4/T16/P01 и прочие gates остаются открыты в прежнем объёме.
