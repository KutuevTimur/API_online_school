# Один разработчик + Codex

Проверено 15.10.2026. Этот workflow — рекомендация для следующих реализационных сессий. Действующий scope берётся из последнего поручения и STATUS; planning package сам
по себе не разрешает код/commit/push/PR/deploy.

## Модели и автоматическая маршрутизация

Актуальная исполняемая политика — AGENTS.md §«Экономный режим Codex».
`.codex/config.toml` задаёт Sol medium для новых сессий и Luna high для субагентов,
с лимитом один субагент. Из внешнего workspace `.codex` ссылается на внутренний:
один источник конфигурации, без gitlink. Не менять глобальные модели других проектов.
Короткие задачи выполняет основной; объёмную узкую безопасную работу делегирует
Luna без истории родителя; сложные и рискованные решения остаются Sol. Усиление
ревью — по конкретному риску/неудачным гипотезам, без постоянной команды агентов.

Технически: доверенный project config задаёт defaults/лимит, но UI override,
существующая сессия и политика клиента могут иметь приоритет. AGENTS автоматически
попадает в инструкции; классификация/момент spawn/границы контекста выполняются
моделью, не детерминированным планировщиком. Текущий родитель не может гарантированно
переключить собственную модель в середине ответа. В среде с другим spawn API передать
те же явные model/effort/ограничения; если это невозможно — один основной агент.
Не запускать скрытый API/CLI inference для обхода клиента, не покупать кредиты.

Plus включает Sol/Luna по текущей документации; доступ Astra не предполагать.
Credit/API тарифы не равны расходу включённого лимита Plus. Процент экономии и
число будущих задач не измерены; не обещать их. Когда владелец просит оценку расхода,
снимать доступный usage до/после связной задачи (окна общие для аккаунта, параллельные
чаты мешают атрибуции). Не опрашивать usage после каждого действия.
Навыки по прежним триггерам SKILLS/AGENTS; новые не устанавливаются ради маршрутизации.

Проверенные официальные источники 21.10.2026:
[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents),
[Config](https://learn.chatgpt.com/docs/config-file/config-reference),
[Plus/usage](https://learn.chatgpt.com/docs/pricing).
Перепроверять при смене клиента/моделей или фактическом отказе, не в каждом чате.

## Начало сессии — 5 действий

1. Открыть внутренний `API_online_school`; проверить repo root, branch, status, SHA. При грязном дереве прочитать diff только относящихся к задаче файлов; не reset/stash/delete пользовательской работы автоматически.
2. Прочитать GPT.md, STATUS.md и одну текущую карточку. rules_project.md — перед кодом; PRODUCT/ARCHITECTURE только relevant разделы. Исторический аудит целиком не нужен в каждом чате.
3. Проверить зависимости и D-решения текущей задачи. Если нет runtime, работать над доступной частью и честно отметить NOT RUN; не объявлять тесты успешными.
4. Назвать ID, ожидаемый результат и 2–4 проверки; перейти к работе. Не переписывать полный план и не задавать уже решённые вопросы.
5. Разрешение на реализацию конкретной задачи покрывает нужные локальные исправления и тесты. Коммит/push/публикация выполняются только в рамках действующего поручения владельца, отдельно фиксируются; не делать их из инструкции навыка вопреки поручению.

## Ветки, коммиты, push/PR

Рекомендация: dev — интеграция, `codex/t03-auth-public-dto` и подобные короткие ветки от проверенной dev. Main — будущие проверенные выпуски, сейчас содержит старый шаблон. Не работать одновременно над одинаковыми файлами в двух чатах. Для одного разработчика обычный checkout проще, worktree нужен лишь для действительно независимой работы.

После разрешения реализации и при сохранённом состоянии:

```sh
git status --short
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c codex/t03-auth-public-dto
```

Это пример последовательности, не безусловный скрипт: если текущая задача уже на ветке, продолжить её; если dirty дерево/расхождение dev, сначала сохранить/разобрать изменения. `pull --ff-only` отказ — повод посмотреть divergence, не force reset. Upstream изменения обсуждать отдельно, не синхронизировать друга поверх MVP без diff.

Один commit — один проверяемый смысл. Пример: `fix(auth): T03 exclude internal fields from public responses`. В commit включать тесты/миграцию/необходимые документы; не unrelated formatting. Stage явными путями, особенно пока docs untracked; проверить `git diff --cached` и отсутствие env/media. Не `git add .` из внешнего `lgg платформа`.

По явному запросу «закоммить и создай PR»:

```sh
git add src/modules/auth/views.py src/modules/users/models_dto.py tests/modules/auth/test_views_auth.py
git diff --cached
git commit -m "fix(auth): T03 exclude internal fields from public responses"
git push -u origin codex/t03-auth-public-dto
```

PR: **head в форке KutuevTimur, base dev того же форка**, не upstream друга и не main по умолчанию. Текст: проблема → новое поведение → проверки/непроверенное → миграции/риски. Пример PR создаётся через gh/GitHub только при авторизации; multiline body передавать файлом. Если Codex создаёт PR, прикрепить ссылку к чату. Merge после checks/review; squash допустим для компактной истории. Не merge красные тесты молча; baseline failures допустимы только явно оценёнными и не затрагивающими release gate. Release main не требует разработки отдельно в main.

До появления CI локальные проверки обязательны. T16 добавляет CI, но это не заменяет визуальную проверку UI и restore rehearsal. Не отправлять логи со student data в PR.

## Проверки по изменению

| Изменение | Минимально полезная проверка |
|---|---|
| DTO/auth | Фактический JSON, отрицательные токены, active, related route tests |
| Permissions | 2 teacher + shared student + other student; list/detail/write/download |
| Migration | Alembic clean install + synthetic prior state + counts/constraints |
| Transactions/files | Failure injection, rollback, retry, concurrent DB sessions |
| UI | Typecheck/build, keyboard + mobile, success/error/empty/loading, E2E затронутого сценария |
| Deploy | Image contents, boot/health, backup+restore, smoke и negative auth |
| Только docs | Ссылки/ID/противоречия/diff; полный pytest не нужен |

Не писать сотни зеркальных tests ради процента coverage. Не прекращать обязательные проверки для экономии токенов: экономить на повторном исследовании и лишнем выводе. Если тест падает: сохранить summary и короткий relevant traceback, сформулировать гипотезу, проверить её; не гонять полный suite после каждой строки.

## Состояния и передача

В STATUS одна строка на задачу: TODO → IN_PROGRESS → VERIFY → DONE; BLOCKED с конкретной причиной/следующим действием. `VERIFY` означает код есть, проверки/ревью не закончены. Отдельно `commit: none/SHA`, `PR: none/url`, `release: none/tag`. Галочка [x] только для DONE; не закрывать задачу от наличия плана, collect-only или непроверенной генерации.

В конце каждой сессии обновить:

- текущую карточку: что реально изменено, команды и результаты, unresolved risks;
- STATUS: задача, ветка/SHA, dirty/untracked, следующий конкретный шаг;
- SESSION_LOG: 3–6 строк с датой, ID, результатом и местом доказательств;
- GPT.md только если поменялся entry point, scope или существенное текущее состояние. Не переписывать его ради отметки «оптимизировано».

Оптимизация контекста отражается фактически: «убран дубль X, ссылка на Y» либо «структура не менялась». Не удалять неуспешные проверки/нерешённые риски ради короткого handoff. Подробные логи — локальный ignored артефакт, в Git только минимальная воспроизводимая запись без ПД.

## Когда новый чат

Новый чат — после завершённого связного результата (обычно карточки), при смене направления backend→UI/infra или когда накопились многочисленные отвергнутые подходы и модель повторяет их. Не обрывать перед тестом только потому, что диалог длинный. Если прерывание необходимо — записать точную незавершённую операцию и VERIFY.

Официальный Codex описывает compact/resume/fork и рекомендует связные задачи вместо одного бесконечного чата; доступность CLI-команд в desktop не предполагать. Автоматическая compaction не заменяет STATUS. Нет универсального правила «новый чат каждые N сообщений/80%»: ориентироваться на связность задачи и качество ответа. Смена модели внутри того же чата допустима при сохранении цели; новый чат не обязан снова исследовать платформы.

## Экономия контекста

Короткий вход + task card + targeted rg/sed. Не копировать пакет в сообщение. Не загружать все навыки, весь diff, полный pip log или 50 страниц документации в каждый чат. Web повторять при изменении зависимостей/перед релизом/для действительно текущей нормы; статические проектные решения переиспользовать. Один основной исполнитель; узкое делегирование по AGENTS, без субагентов для мелочей. При review ограничить область и критерии; не просить «сделай идеально всё». Для незнакомой библиотеки сначала официальный API нужной версии, затем код.

## Агент ведёт владельца

Обязательное правило общения — AGENTS.md, раздел «Вести владельца по процессу». Владелец задаёт результат и принимает существенные решения; агент выбирает следующий технический шаг, проверки и доступные навыки. При необходимости ручного действия даёт конкретные шаги и проверку успеха. При смене модели/сессии или необходимости установки навыка даёт готовый текст следующего сообщения. После проверенной задачи сам напоминает о сохранении в GitHub и предлагает конкретный commit/push/PR запрос, сохраняя действующие ограничения на выполнение.

Финальный ответ по задаче заканчивается краткой практической передачей: что нужно от владельца сейчас, какой следующий ID и продолжать ли текущий чат. Если участие не нужно, прямо сказать это. Не превращать эту передачу в повторение всего workflow.

## Когда подключать владельца к проверке и настройке

На каждом завершённом пользовательском сценарии оценить, есть ли полезная ручная проверка. Если есть — агент сам предлагает её после собственных проверок и даёт короткий сценарий: «Открой [проверенный адрес] → сделай [действия] → должно получиться [результат] → сообщи [конкретные наблюдения]». Для фото включить читаемость формул на телефоне и компьютере; для интерфейса — понятность действий. Не поручать владельцу разбор traceback или запуск всего pytest, если агент может сделать это сам. Если пока готовы только инфраструктура/внутренняя логика, объяснить, когда появится первый доступный экран/сценарий.

Ручную приёмку учитывать отдельно: «не требуется / ожидает владельца / пройдена / замечания». В STATUS/карточке сохранять только актуальное состояние и критерии, не дублировать весь отчёт. Если ручной тест обязателен и ещё не выполнен, соответствующий критерий остаётся открытым. Результат пользователя записывается по факту.

Для инфраструктурного решения сначала сверить ENVIRONMENT/README/config. Пока работа локальная, использовать штатное local storage: сейчас Compose предусматривает dev volume `lgg-dev_media`, тесты — временные каталоги pytest; фактический mount/path проверять перед объяснением пользователю. При запуске backend непосредственно на хосте путь определяется MEDIA_ROOT/config.paths, поэтому Docker volume и папку компьютера не называть одним и тем же. Перед первым upload агент объясняет место хранения и persistence, не просит владельца заранее спроектировать папки. Вопросы о параметрах Timeweb, регионе и S3 — перед зависимым этапом, как D09/F06.

Запрос владельцу строить так: «Сейчас нужно решить X, потому что следующий шаг Y. Рекомендую Z: польза…, существенный компромисс…. От тебя: конкретное подтверждение/действие». Если выбора нет и нужен доступ/настройка, дать точный список нужных несекретных сведений и безопасный способ внесения секретов. Не повторять согласованные сведения, не присылать постоянные меню вариантов. Для Git/model/skill/session сохраняется тот же принцип: подсказка при реальной необходимости, самостоятельная работа между такими точками.

## Глубокий аудит и обоснованная оптимизация — только по запросу

1. Зафиксировать scope и git baseline, открыть STATUS и последнюю CHECKUP;
   не повторять свежий аудит без изменений. Составить компактную карту файлов,
   размеров/дублей и ссылок через rg/AST; generated/vendor/историю не читать целиком.
2. При достаточном объёме делегировать Luna одну read-only сверку документации:
   актуальность ссылок, дубли, противоречия с PRODUCT/STATUS; до 10 находок с путями.
   Основной проверяет код/архитектуру и риски. При отдельном сложном вопросе —
   последовательный Sol high reviewer с reproducer, без второго общего аудита.
3. Каждая находка: доказательство, влияние, минимальная правка, проверка.
   «Нет AST refs» не доказывает dead code: проверить rg, dynamic imports, routes,
   migrations, scripts, tests и внешние контракты. Сомнительное оставить кандидатом.
4. Если запрос разрешает оптимизацию, выполнить доказанные локальные улучшения
   и relevant gates; аудит без разрешения правок остаётся read-only. Исторические
   evidence не стирать, дубли требований заменять ссылкой на принятый источник.
   Не расширять scope до новых функций/смены стека/DB очистки/commit/deploy.
5. Результат записать в одну датированную CHECKUP (или дополнить текущую), STATUS
   и 3–6 строк SESSION_LOG. Оставить список отложенного и NOT RUN; не создавать
   новую систему планов. Проверки платформы/ручная приёмка остаются по карточкам.
