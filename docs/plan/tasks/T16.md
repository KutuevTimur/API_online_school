## T16.1 — регрессия и понятность полного MVP

**Регрессия student-расписания, уже реализованного21.10.2026.**
Не повторять реализацию выбора недель и отметок дней. В этом этапе проверить
их вместе с полным MVP. Полные требования — PRODUCT§5 и
[T15a: выбор недели](T15a.md#дополнение-выбор-недели--16102026):
- «Прошлая неделя / Текущая неделя / Следующая неделя», видимое и доступное
  выделение открытой недели, честный диапазон дат и сохранение дальнего листания.
- Ненавязчивые отметки дней с занятиями с учётом view; наличие занятий и выбранный
  день различимы, доступное описание не полагается только на цвет.
- Сохранить дизайн; проверить360px/desktop/keyboard, URL/reload/назад, смену недели
  и года/фильтра, пустой день и выбранный день с занятиями. После реализации
  включить в полный regression baseline. Реализация есть, полный matrix ещё NOT RUN.


1. Изолированный E2E backend/test PostgreSQL и media на **отдельном target**, не
   использовать реальную dev DB для fixtures. Actual engine guard; отдельный проект/
   ports, исключить параллельный reset pytest/E2E одной БД. Можно использовать
   disposable sequential lgg-test после preflight; запретить concurrent suites.
2. Seed:2 teacher/shared student/другой student/admin, active/read-only/debt,
   draft/submitted/checked, PDF/photo. Секреты генерировать в job/runtime, не commit.
   Браузерные storageState игнорируются Git; traces synthetic, secrets redacted.
3. Проверить реальные маршруты: invite/login→teacher create/course/lesson/issue→
   student3 photos/append/delete/submit/edit→version-aware review→student result→
   archive/read/download→admin link/restore/purge. События и очередь согласованы.
4. Расширенный teacher MVP: создание из слота/поиск своих с нормой, регулярность
   по принятому D11 (повтор/продление без дублей, отдельные перенос/отмена),
   быстрый перенос с подтверждением, недобор с нулевыми учениками; недельные суммы
   строго по D12, разные ставки одного student у двух teacher, неполная цена,
   история ставки и архива. Проверять весь недельный агрегат, не страницу списка.
   DnD не обязательный gate, пока отдельно не реализован; при включении — cancel/
   confirm и доступная замена кнопкой. Ученические недели/отметки уже есть в коде;
   прошлые targeted проверки не заменяют полный baseline этого этапа.
5. Negative matrix: чужой course/lesson/homework/submission/file_id, direct link,
   changed recipient query, deactivated/reset/logout, ended/gap/revoked,
   cross-tab refresh. Browser-route guard не считается server auth проверкой.
6. Fail paths A12:422/413/quota/409/401/403/404/network timeout/offline/partial
   upload/unknown commit, browser back/reload и draft сохранность. Проверять по
   наблюдаемому состоянию API/UI, не только screenshot без console errors.
7. Chromium desktop1280 и mobile390, WebKit390 для iPhone flow, Firefox desktop;
   narrow360, tablet768, zoom200%, keyboard-only, reduced motion, opened select/
   date popup и long Cyrillic names/filenames. Axe scans ключевых экранов, manual
   keyboard/focus дополняет axe. Снимки со стабильными clock/seed/fonts, не
   snapshot всего DOM вместо проверки поведения.

Критерии: нет открытых P0/P1, все обязательные paths green и состояние данных
подтверждено; при flaky тесте расследовать race, не add skip/retries ради зелёного.
Targeted component/E2E при разработке; полный frontend matrix здесь один раз
после исправлений, backend full guarded pytest + migrations clean/prior-state.
Команды exact из package.json/README, real results в карточке; не заявлять полный
набор по одному Chromium smoke. Browser engines/runtime пересверить по фактическому lock.

Ручная приёмка **обязательна**: владелец/student substitute и teacher проходят
маршрут без подсказок, записать шаги, остановки/непонятные подписи, ожидание и
результат. Предлагаемый ориентир: найти ДЗ за 1 мин, отправить 3 фото за 3 мин без
учёта сети, открыть очередь/выдать результат без объяснений. Это диагностические
ориентиры, не SLA. Любая невозможность выполнить обязательное действие блокирует
G3; мелкая вкусовая полировка может идти отдельной задачей после MVP.

## T16.2 — повторяемые checks в GitHub Actions

Зависимость .1. Jobs: backend unit/guard + PostgreSQL functional + migrations;
frontend npm ci/ls/typecheck/lint/format/unit/build/api:types:check;
E2E synthetic (сначала Chromium smoke + WebKit upload/refresh, полный matrix
по manual dispatch/перед release), a11y/critical visual states.
Node24.22, Python/project requirements и browser versions pinned lock;
Actions SHA pin после проверки официального upstream (уточнить **тогда**, не
выдумывать SHA сейчас). Permissions contents:read по умолчанию, без production
secrets/deploy jobs/pull_request_target с чужим кодом. Artifact retention7days,
sanitize traces/token/cookie/body. Cache только dependencies, не DB/media/secrets.
Dependency/license scan оценивать по достижимости; fixes scoped, без npm audit fix --force.

Приёмка: reproduce локально; после отдельного разрешения push — зелёные GitHub
checks на конкретном SHA. До push можно принять локальную конфигурацию как
VERIFY: «Удалённый CI не проверен», не утверждать CI DONE. Если владелец пока не
разрешает GitHub, это блокирует только удалённый критерий, независимые docs T17
можно готовить, публикация G4 ждёт green на release SHA.
Риск: CI fixture затронет dev/поглотит секрет; отрицательный guard test обязателен.
Ручная проверка: владелец видит checks URL/статус после разрешённого сохранения,
разбирать traceback агент обязан сам. Следующее T17.1.
