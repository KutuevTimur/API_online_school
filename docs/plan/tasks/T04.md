# T04 — атомарная refresh-ротация и отзыв

Зависит T03. Sol high. Если дизайн транзакции не складывается после двух разных проверенных гипотез — узкое ревью Astra, не переписывание auth.

## Файлы и контракт

`auth/token_service.py`, `auth/views.py`, `refresh_tokens/{models,models_dto,repository,service}.py`, `users/models.py` (auth_version), migration, `tests/modules/auth/` и refresh-token tests. Сохраняем random refresh token и JWT, bearer API до T14.

Предложение реализации: row-level `SELECT ... FOR UPDATE` по digest; проверка expiry/revoked/user.active, отметка старого revoked и вставка нового token в **одной** транзакции сервиса. Репозиторий не commit. Вложенный create_token не commit самостоятельно; генерацию и запись отделить от завершения транзакции. Unique digest. Digest SHA-256 пригоден для криптографически случайного высокоэнтропийного refresh (это не алгоритм хранения пользовательского пароля).

## Последовательность

1. Добавить digest/session identifier/family и нужные поля; raw secret возвращается один раз. Существующие токены при миграции отозвать и попросить вход заново; raw token удалить из хранения после перехода. Для внешней БД сначала inventory/окно обслуживания, не silent migration.
2. Ротация блокирует строку, перепроверяет revoked/expiry после lock, пишет новое поколение. Commit один. На error rollback сохраняет прежнее действительное состояние. Не генерировать два валидных потомка.
3. Replay возвращает 401; политика семейства — отзыв активного потомка при подтверждённом повторном использовании, без logout чужого пользователя. Документировать, что строгий replay может потребовать повторного входа при гонке вкладок; T14 делает single-flight.
4. Logout требует current_user, проверяет принадлежность refresh; чужой токен не удаляется. Повтор собственного logout идемпотентен по согласованному 200/204 контракту без раскрытия token existence.
5. Password change/reset отзывает все refresh пользователя, повышает auth_version; access проверяет version и active. JWT старого формата на переходе отклонить/потребовать вход, не бесконечный compatibility bypass.
6. Записать срок access/refresh как конфигурацию с безопасными default (A03); проверить timezone-aware timestamps на asyncpg.

## Обязательные тесты

- Valid refresh → один новый; старый replay → 401; expired/revoked/inactive → 401.
- Два независимых AsyncSession одновременно обновляют один токен: максимум один успех; policy replay/family воспроизводима. Не тестировать «конкуренцию» двумя await подряд в одной session.
- Инъекция ошибки между revoke и insert → rollback, нет half-rotated session.
- Logout A с refresh B не меняет B; password change A не отзывает B.
- После password change старые access/refresh A запрещены, новый login работает.
- В БД/логах нет raw refresh, публичный ответ не содержит digest.

## Приёмка

- [x] Все тесты выше проходят на PostgreSQL; SQLAlchemy transaction boundary проверена чтением diff.
- [x] Миграция проверена на synthetic token snapshot; no raw secrets after upgrade.
- [x] Документирован переход с принудительным re-login; cookie bridge не притворяется реализованным.

Риски: nested commit, deadlock (брать locks в одном порядке), asyncpg naive time, браузерный retry, потерянный успешный ответ. Не добавлять Redis ради решения row-lock задачи.
