## 1. Q01 — файловая изоляция аватаров (P1, первая)

Файлы: handlers_files/converter_images.py, users/courses service+views, storage/handler adapter по необходимости; tests для своего/чужого пользователя и курса. Все пути относительно src/modules.

- Убрать клиентский filename из временного/final filesystem key; генерировать серверное opaque имя. Существующие avatars читаются до успешного перехода.
- Применить безопасные storage primitives/проверку содержимого, ограничить bytes/pixels/frames/timeout. Не оставлять синхронное декодирование анимации без лимитов в event loop. Лимит аватара определить как технический параметр в существующем config и показать понятную ошибку; не внедрять новый облачный storage.
- Ответ upload не должен возвращать raw пользовательский файл с непроверенным client MIME/filename inline. Вернуть безопасный согласованный metadata/URL либо нормализованный WebP; обновить tests/README для клиента T14.
- Regression: fixture двух teacher/student, существующий чужой аватар; PATCH собственного avatar с filename, содержащим `/../../avatars_users/{другой user_id}/avatar.webp`, и invalid bytes. Получить контролируемый 4xx; чужой файл и все указатели неизменны. Проверить аналогичный course avatar, absolute/backslash/normal filename, валидное фото, oversized/pixel/animation и symlink case.

## 2. Q02 — сохранность при замене

- Новое фото проходит validate/normalize в новом объекте, DB pointer меняется в транзакции, прежний объект удаляется только после commit с повтором/компенсацией.
- `avatar_file` использует согласованную с хранением ссылку, а не оставшийся фиксированный путь после перехода.
- Ошибки decode, write, DB commit, повтор удаления и отмена запроса не уничтожают прежний avatar. При uncertain COMMIT учитывать уже реализованную защиту T12.
- Regression для UsersService и CoursesService: старый файл+pointer → ошибка нового файла → прежний GET отдаёт прежние bytes. Отдельно успешная замена и отказ DB. Admin audit откатывается вместе с действием.

## 3. Q03 — DELETE ДЗ при наличии ответа

Предложение безопасного минимального исправления: наличие любой попытки/истории → 409, ДЗ/ответы/файлы/placements неизменны. Отдельно checked остаётся закрытым. Если владелец предпочитает иной исход, сначала согласовать сохранение истории, не добавлять молча каскадное уничтожение решений. Не удалять строку и ловить FK как штатную бизнес-проверку.

Regression через API: draft, submitted, историческая non-working попытка и checked; отсутствие ответов — существующий разрешённый DELETE, cleanup только его файлов. Проверить rollback и отсутствие чужих изменений, родительский course lock при конкуренции с созданием ответа. Нынешнее нарушение подтверждено PostgreSQL, SQLite недостаточна.
