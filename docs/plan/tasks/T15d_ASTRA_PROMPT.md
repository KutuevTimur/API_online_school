4. Осмотр реального интерфейса

Обойди все доступные teacher разделы и типовые вложенные экраны по router/меню:

  прокрутка, создание/редактирование, постоянное/разовое, итог недели;
• /teacher/students — поиск/классы/список17; профиль ученика и его учебный workspace,
  история/занятия/настройки/цена/приглашение, доступные вторичные действия;
• /teacher/lessons/:id — будущая и проведённая встреча, материалы/ДЗ/тема,
  выдача/загрузка/состояния файлов, ссылки, управление и доступный архив;
• /teacher/review и /teacher/review/:id?homework_id=... — очередь, решение,
  просмотр PDF/фото, состояние checked/submitted, форма результата;
• /notifications и /profile — в роли Тимура;
• доступные teacher courses/archive и связанные формы/диалоги — если присутствуют
  в текущем UI; не придумывай отсутствующие разделы и не навязывай их в главное меню.

Один заполненный представитель на тип страницы; второй — только для существенно
другого состояния (пустой workspace, материал отсутствует, текстовый/файловый ответ,
проверенная работа). Не открывай всех17 одинаковых профилей. Пройди сценарии:
«следующий урок → ученик → материалы → ответ → проверка → место результата» и
«вечером найти недовыданные конспекты/ДЗ» без завершающих mutations.

Desktop1280–1440, mobile360, tablet768 — targeted для навигации/календаря и спорных
раскладок, не полный cross-product всех страниц/состояний. Проверяй реальный CSS
innerWidth: viewport override/IAB capture иногда расходятся и обрезают снимок.

scroll/sticky, открытые select/dialog, несмешение статусов черновика/отправки.
Не вызывай ошибки сети/сессии и не меняй сервер ради иллюстрации; неувиденные
empty/loading/error состояния проверяй по реализации и помечай «по коду».
Не называй это E2E/a11y PASS без реального соответствующего прогона.

5. Что именно оценить и предложить

Не ограничивайся «добавить воздуха/цвета». Для каждого раздела покажи:
— зачем учитель сюда приходит, что видит первым и какое действие главное;
— где именно интерфейс замедляет/путает и каким наблюдением это подтверждено;
— конкретную композицию desktop/mobile: порядок блоков, колонки, плотность,
  размер и место имени/класса/времени/темы/статуса, что раскрывать по запросу;
— точные подписи и иерархию действий primary/secondary/subtle/danger, их место,
  близость к объекту, критерии видимости, без потери существующих функций;
— назначение цвета, поверхности, borders, typography, spacing, icons и состояний;
— как рекомендация переиспользует canonical компоненты и не меняет контракт.

Отдельно предложи общую навигацию и визуальную систему для teacher: где полезны
верхнее меню/локальные вкладки/breadcrumbs/мобильное меню, что оставить постоянным,
что контекстным. Выбери один обоснованный основной вариант, не набор модных меню.
Сохрани узнаваемость голубого/мяты/Manrope. Дай компактные token предложения
(HEX/семантическая роль, контраст), уровни кнопок, статусов и группировки карточек.
Критикуй нынешнюю реализацию независимо, но не заменяй согласованный стиль личным
вкусом. Не путай красивый маркетинговый dashboard с рабочим кабинетом учителя.

Мини-анимации допустимы как рекомендации: конкретный trigger/назначение/duration,
reduced-motion и отсутствие layout shift. Никаких долгих вступлений, декоративных
счётчиков, прогрессов и выдуманной статистики. Новую функцию, новую бизнес-семантику
или потребность API помечай отдельно «вне текущей frontend доработки».

в чате. Один проход всех типов экранов, затем максимум один целевой возврат для
