## Что считаем MVP

Учитель добавил ученика → назначил занятие → выдал материалы и ДЗ → ученик
отправил текст/файлы → учитель нашёл работу, открыл все вложения и проверил точную
версию → ученик увидел оценку, комментарий и файлы проверки. Весь путь уже имеет
локальную реализацию; его наличие не закрывает ручную приёмку и финальную регрессию.

Для **реального** запуска также обязательны: admin кабинет, согласованная недельная
статистика расширенного teacher MVP, изоляция доступа, сохранность файлов/архива,
три роли и телефон, повторяемые проверки, production-конфигурация, доказанный
restore БД+файлов, допуск ПД и разрешение публикации. Одна работающая роль или
локальный HTTP200 не означают готовый MVP. Источники: PRODUCT§4–9, DECISIONS,
ARCHITECTURE A09–A13, DESIGN; никаких новых требований этот список не вводит.

## Как поддерживать план при уточнениях

- PRODUCT — принятое требование; DECISIONS — принятое/открытое решение; ARCHITECTURE — контракт/общий owner; DESIGN — вид. Карточка ссылается на них и содержит результат/проверки/остаток.
- STATUS кратко хранит текущий факт, SESSION_LOG — датированную историю. Исторические FAIL/NOT RUN не стирать и не выдавать за действующий блокер после подтверждённого исправления.
- Новая идея: обозначить необходимость до MVP либо отложить в F backlog; не расширять текущую реализацию попутно. Простые модули/DTO/общие компоненты сохранять, без универсальных движков.
- DONE требует критериев и обязательной ручной приёмки. PASS относится только к конкретной выполненной команде/сценарию; наличие теста и collect-only — не PASS выполнения.
