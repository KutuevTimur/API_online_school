## Экономный режим Codex — применяется автоматически

Локальный `.codex/config.toml`: основной GPT-6.1 Sol medium, субагент Luna high,
максимум один субагент одновременно. Явный выбор модели в UI/сессии приоритетнее.
В начале оценить риск молча; не запускать отдельного агента для классификации.
- Простая короткая правка/один поиск/одна команда: выполнить самому, без делегирования.
- Объёмная механическая работа по готовому образцу или отдельный поиск/сверка:
  один субагент GPT-6 Luna high допустим только при конкретной ожидаемой экономии
  общей работы/контекста с учётом постановки и проверки. По умолчанию выполнять
  самому; параллельность и дешёвая модель не доказывают экономию. Не дублировать
  поиск/реализацию worker; для короткой правки worker не нужен.
- Бизнес-логика/UI поток/несколько связанных слоёв: основной Sol; передавать Luna
  только самостоятельную безопасную часть. Auth/tenant/SQL/миграции/удаление/media/
  concurrency проверяет Sol; короткий файл не делает такой риск простым.
- Нерешённый invariant, конфликт требований, две разные неудачные гипотезы:
  остановить повторы; один узкий reviewer Sol high. Astra low — лишь если доступна
  и остаётся конкретный сложный риск после Sol; не обязательная зависимость Plus.

При spawn задавать `fork_turns="none"`, явные `model` и `reasoning_effort`;
передать цель, разрешённые пути, нужные требования/инварианты, проверки и stop-условие.
Ответ: результат, пути/строки, команды/PASS/FAIL/NOT RUN, остаток — до 15 строк.
Без дочерних агентов у субагента, общего reread проекта, установки/commit/push;
один writer на файл. Безопасный worker может править только выданные пути;
основной проверяет diff/релевантный gate, не повторяет всё исследование.
Если spawn/модель недоступны — продолжить основным; не делать циклов попыток и
не обходить через API/отдельный платный процесс. Один неудачный worker → основной.
Не порождать «планировщик → исполнитель → ревьюер» для каждой задачи.

Контекст: вход один раз за сессию; текущую длинную карточку читать по оглавлению/
актуальному subsection, дальше только relevant фрагменты. AST update после смены
кода/ветки; symbol/outline/refs с limit, затем исходник участка и rg для полноты.
Не перечитывать историю/полный diff/все навыки и не повторять успешный gate без
новых изменений. Handoff — в существующей карточке/STATUS/SESSION_LOG.
По запросу «глубокий аудит/оптимизация проекта» применять режим WORKFLOW;
сам запрос продолжить разработку такого аудита не включает.

Уточнение владельца21.10 после T15b.4: **минимальный расход — приоритет** при
сохранении обязательных проверок и данных. Разбор — docs/plan/tasks/CODEX_SETUP.md.
- Читать нужные диапазоны; избегать больших cat/diff с обрезанным выводом.
- До команды проверить cwd/пути/binary и контракт по исходнику; не угадывать
  HTTP-код/redirect или путь skill-скрипта. После ошибки остановить зависимые
  действия, исправить причину и лишь затем запускать следующие команды/тесты.
- В разработке — scoped tests; дорогой полный gate — после готовности кода,
  повтор только при релевантном изменении/ошибке. Успешные независимые группы
  не повторять из-за исправления одной упавшей. Обязательные gates не пропускать.
- До DB тестов подготовить изоляцию и browser fixture; дождаться readiness
  нового сервиса. Не обнаруживать несовместимость fixture после долгого прогона.
- Не утверждать измеренную экономию без метрик: время и число агентов не токены.

## Код и данные

`outline PATH`, `refs NAME`; определения уточнять `--in-file PATH`.

Сохранять backend и D01–D06, без попутного refactor/новых функций вне MVP.

Только synthetic до P01. Не показывать .env/секреты/реальные ПД/dumps в чат/Git/CI.

## Доведение до MVP — правило владельца 20.10.2026
Сначала только необходимое для законченного пути: запись → материалы/ДЗ → ответ
ученика → получение и проверка учителем → результат ученику. Не считать поток
готовым, если одна роль отправила данные, а другая не может их найти и открыть.
Перед новой идеей прямо обозначать: нужно для MVP сейчас или лучше после MVP,
и почему. Предлагать один минимальный вариант; необязательные улучшения оставлять
в backlog, не реализовывать попутно. Это не отменяет согласованные требования,
границы полномочий, безопасность, сохранность данных и обязательные проверки.
Код простой и расширяемый: существующие доменные границы, явные API-контракты,
общие компоненты для повторяемого поведения. Не делать временные обходы, которые
потребуют переписать основу; не строить универсальные движки/абстракции под
гипотетические функции. Точку расширения добавлять там, где её требует текущий сценарий.
Понятный UX/UI — критерий готовности MVP для обеих ролей. На экране очевидны
главное действие, состояние и следующий шаг; вторичное раскрывается по необходимости.
Убирать дубли и технический текст. Использовать принятую палитру: голубой — основное
действие/выбор, мята — успех/результат, красный — ошибка/требует внимания. Цвет всегда
сопровождается текстом, сохраняются контраст, клавиатура и mobile. Принятый дизайн
сохранять; большой редизайн не подменяет завершение основного учебного пути.
